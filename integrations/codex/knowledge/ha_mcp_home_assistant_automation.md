# ha-mcp — Home Assistant MCP Server

Source · https://github.com/homeassistant-ai/ha-mcp · homeassistant-ai · MIT · v9.2.0, commit `635cb93b23ef8657d9f62f68cb0fd234bf16056d` · verified 2026-11-18 · scope: public

## What it is

An MCP server that lets an agent configure, debug, and control Home Assistant: entities, automations/scripts/scenes, dashboards, helpers, areas/zones/labels/groups, calendars, todo, backups, add-ons, HACS, Z-Wave/Zigbee/Thread/Matter radios, history/logs/traces, energy preferences, and system health/restart.

Optional integration. Connect a Home Assistant server that the user controls through the upstream configuration for the selected transport and client.

## Why it matters

Two separate values, and only one is available now:

1. **Smart-home control (deferred).** Real capability, but requires HA + hardware + a token. Zero day-job value today.
2. **MCP safety patterns (available now, high value).** This repo is a mature example of how to expose a dangerous tool surface to an agent. the user builds and reviews agent tooling for his squad; these patterns transfer with no HA dependency.

## Key concepts

- **Tool annotations.** Every state-mutating tool carries `destructiveHint=true`. Read-only tools do not. This is the blast-radius signal an agent should respect.
- **`READ_ONLY_MODE`.** Server-side switch that removes write capability entirely.
- **Beta gating.** 8 tools are off by default behind feature flags.
- **Tool search mode.** `ENABLE_TOOL_SEARCH=true` replaces the 79-tool catalog with 4 proxies (`ha_search_tools`, `ha_call_read_tool`, `ha_call_write_tool`, `ha_call_delete_tool`) + 7 pinned tools — a context-budget pattern worth borrowing.
- **Best-practices gate.** 6 `ha_config_set_*` writes are hard-blocked until an acknowledgement key from `ha_get_skill_guide` is supplied.
- **Auto pre-edit backups.** `ENABLE_AUTO_BACKUP=true` by default.

## Install

Python **>=3.14,<3.15** is a hard upstream pin. ~35 runtime deps (httpx, pydantic, starlette/uvicorn, authlib, cryptography, pydantic-monty); fastmcp/mcp/websockets are vendored.

```bash
# stdio (upstream explicitly does NOT recommend this — see limitations)
uvx --python 3.14 ha-mcp@latest

# Streamable HTTP
uvx --python 3.14 --from ha-mcp@latest ha-mcp-web

# Docker
docker run -d --name ha-mcp -p 8086:8086 \
  -v ha-mcp-data:$HOME/.ha-mcp \
  -e HOMEASSISTANT_URL=... -e HOMEASSISTANT_TOKEN=... \
  ghcr.io/homeassistant-ai/ha-mcp:latest ha-mcp-web
```

Upstream prefers the **in-process HACS/Marketplace integration** (HA ≥ 2026.8.0) or the HA add-on over stdio.

## Configuration

Required: **`HOMEASSISTANT_URL`**, **`HOMEASSISTANT_TOKEN`** — note these are *not* `HA_URL`/`HA_TOKEN`. Missing either → exit 1.

Token: HA UI → profile → Security → Long-lived access tokens → Create token. Admin recommended; a dedicated local-only admin person is safer than the user's own account. Remote/Nabu Casa URLs work (`https://<domain>` or `https://xxx.ui.nabu.casa`).

Optional: `HA_VERIFY_SSL`, `HA_TIMEOUT=30`, `HA_MAX_RETRIES=3`, `ENABLE_WEBSOCKET=true`, `READ_ONLY_MODE`, `ENABLE_TOOL_SEARCH`, `DISABLED_TOOLS`, `PINNED_TOOLS`, `ENABLE_AUTO_BACKUP=true`, `HA_MCP_DISABLE_SETTINGS_UI=1`, `FASTMCP_SHOW_SERVER_BANNER=false`. HTTP: `MCP_HOST` (default `0.0.0.0`), `MCP_PORT=8086`, `MCP_SECRET_PATH=/mcp`.

Start with read-only mode using the upstream connection instructions. Keep the endpoint and credential in the active client configuration.

## Limitations and safety warnings

- **stdio is explicitly "not recommended"** upstream — known transport hangs (issue #1713). It also spawns a **detached loopback settings-UI sidecar by default**; set `HA_MCP_DISABLE_SETTINGS_UI=1`.
- **Legacy SSE removed.** `ha-mcp-sse` is gone; Streamable HTTP only. SSE clients get 405.
- `SECURITY.md`: the MCP client is a **trusted principal** — prompt injection is the client's problem, not the server's. In standard HTTP mode, **URL-path secrecy is the only auth**. Single-tenant. **DNS-rebinding guard OFF by default.** Token permissions = HA permissions.
- `ha_restart` → 1–5 min downtime.
- `ha_config_set_yaml` **re-serializes the whole file**; `action:remove` deletes an entire top-level key; the config check has blind spots.
- `ha_manage_custom_tool` runs sandboxed Python — **the sandbox is not a security boundary**.
- No documented rate limits.
- **Without HA, almost nothing is reusable.** The bundled best-practices skills are a git submodule (`homeassistant-ai/skills`) — empty in a plain clone, shipped in PyPI wheels. `rules/` are ast-grep dev lint rules; `templates/` is only a changelog Jinja file. No reusable automation/prompt library.
- A public demo exists (`https://ha-mcp-demo-server.qc-h.net`, token `demo`, resets weekly) but it is **third-party hosted** — do not send anything sensitive to it.

## How the agent should use it

- Confirm the server, scope, and authorization before registering the integration.
- For an authorized Home Assistant instance: prefer in-process or Streamable HTTP over stdio, start with `READ_ONLY_MODE=true`, keep `ENABLE_AUTO_BACKUP=true`, and treat every `destructiveHint=true` call as requiring explicit confirmation.
- **Borrow the safety architecture now** in related agent tooling: read-only default mode, per-tool destructive annotations, pre-edit backups, an acknowledgement gate before dangerous writes, and a tool-search proxy mode to cut context cost. 
- If a RuView presence sensor is ever added, it feeds HA automations — never health claims.
